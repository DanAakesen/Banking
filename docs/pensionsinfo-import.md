## Upload and review

Pension offers owner-authenticated PDF/JSON upload in Live and server-generated fictional originals in shared Demo. Arbitrary visitor files are rejected in Demo. The upload action retains an encrypted original and receipt, but changes no wealth records. Failed, unsupported or cancelled parsing leaves the original/receipt available for retry or manual review. MIME, PDF header, byte limits and same-origin/session checks apply. No uploaded filename or PDF metadata is stored in the financial model.

Review shows the original download, parser version/hash, upload date, report date, per-balance source date, source page/section/unit, match status, unknowns and coverage warnings. The owner can edit numeric values and product labels/dates and map agreements onto existing products before explicitly approving selected values and acknowledging extraction limits. Server-owned provenance and identities cannot be replaced by client input. A changed value is marked `UserEdited`. Confidence means a matched text pattern requiring human review, not a claim of accounting accuracy.

Only the reported saved balance of each selected agreement updates current pension capital. Its child components are explanatory. Equal payout rows remain distinct source observations; insurance observations are never summed and may repeat a policy. Two ratepension components and a lifetime component under one agreement remain distinct, without creating three duplicate products. A difference between the reported total and rounded component sum is shown and preserved; there is no balancing entry. Older reports enter history without overwriting a newer current observation. Existing product IDs and optimistic concurrency tokens remain in use.

Scenario tables, ATP/public pension payout entitlements and insurance are separate from capital. Scenario units remain annual, monthly or unknown; no automatic conversion or assumed tax treatment. Before-tax/today's-money assumptions appear only when matched in the source. Unmatched details, terms, source dates, providers and table structures require review in the original. Provider recognition is deliberately limited; an unrecognized provider requires manual review. The parser does not extract holdings, allocation or actual historical investment returns. It does not claim complete coverage of all PensionsInfo versions.

## History and comparison

`PensionDocuments` deduplicates encrypted file contents by SHA-256 within the workspace. Each upload creates a separate `PensionUpload` receipt. `PensionSnapshots` holds immutable approved structured values and selected product mappings; uploads link to a canonical accepted snapshot. Repeating an unchanged approval produces no additional snapshot or product. For an identical file that previously received reviewed edits, the UI can display and link to that accepted snapshot without replaying financial writes. A deliberate revision creates a correction rather than overwriting a snapshot.

Same-date corrections for the same selected agreement set require the previous snapshot ID and explicit confirmation. The previous version and its original remain selectable. Different product coverage is not silently combined. History lists 50 receipts per page; the development table shows at most the latest 200 non-superseded approved report observations and discloses truncation. Originals remain reachable through paged upload history.

The development table compares reported capital subtotals for the listed products/currency and shows their source dates. Annual contributions appear only when explicitly reported in that unit for every included product. Returns stay unknown. Balance changes are not inferred returns, deposits are not invented, currencies are not mixed, and there are no fabricated intermediate observations. Old snapshots are not summed into current 360 capital. Once approved pension history exists, the older fictional Demo contribution/return split is suppressed. A confirmed manual pension save also creates a dated structured original and receipt; pre-existing records are not backfilled with invented history. Existing JSON preview and manual editing remain usable; retained JSON file uploads use the new owner upload route.

## Protection and parser limits

Originals are stored as Data Protection ciphertext in the existing workspace SQL database, scoped by hosting key ring, mode and Demo scope. Existing `/home/Banking` keys and protection certificate remain essential to recovery. Only explicit receipt/snapshot DTOs are returned. Original downloads require the normal session/owner workspace authorization, use fixed attachment filenames and `no-store, private`, and carry a sandbox CSP. The browser downloads via authenticated mode-bound fetch. No raw PDF text, original or metadata is supplied to the advisor/AI context, logged, interpreted as instructions or sent to OCR/LLM services. Existing approved capital facts remain ordinary financial context.

[PdfPig 0.1.16](https://www.nuget.org/packages/PdfPig/0.1.16) is a pure managed Linux-compatible Apache-2.0 dependency. Primary [versioned parser documentation](https://github.com/UglyToad/PdfPig/tree/v0.1.16) was checked; extraction groups words by page coordinates rather than treating `page.Text` as reading order. Dependency versions are locked and NuGet audit remains enabled.

PDF parsing runs in a separate `--pension-pdf-worker` process, before web-host configuration. The child's environment contains only runtime lookup variables, a 256 MiB GC limit and disabled diagnostics, without application/provider configuration. There is one concurrent parser, a 20-second deadline, 384 MiB working-set check, bounded input/output, and whole-child-tree cancellation. Limits: 8 MiB PDF, 80 pages, 60,000 letters/page, 600,000 total letters, 512,000 output characters. Encrypted, blank/scanned, malformed, excessive and unrecognized reports return safe codes. JSON remains limited to 60 KB. Full reviewed approval payloads have a separate bounded 768,000-byte limit. No normal Linux business-host/database fallback is introduced.

Existing recovery archives include originals and snapshots; portable archives decrypt originals only inside the outer passphrase-encrypted archive and re-protect on restore. Non-portable recovery still requires the original key ring. Production SQL and `/home` backups retain their established responsibilities. No deletion, retention expiry, new storage resource or new permission is introduced.
