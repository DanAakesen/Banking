## Confirmed requirements

- A budget contains entries. Each entry has a name, amount/currency and frequency: every month, three months, six months or year.
- The entry dropdown offers Income, Expense and Savings. Savings is stored as Expense with the existing Savings marker; the three UI choices preserve the calculation contract without a separate checkbox.
- Show monthly-equivalent Total income, Total expenses (excluding savings), Planned savings and Available to spend (Danish: Rådighedsbeløb). Available to spend equals income minus other expenses minus planned savings. These are planned budget figures, not measured bank cash flow or achieved savings.
- When no budget exists, start with manual entry, rather than making transaction suggestions the primary action.
- Support several named budgets in each workspace. An active budget determines which plan budget-dependent metrics use.
- Transaction-based creation asks whether to merge into existing entries/budget or create a new budget when existing budgets are available.
- Users review and adjust suggestions manually. Do not overwrite their existing entries silently.
- Improve the page's visual hierarchy and clarity. Budget comparison and projections based on changes are later features.
- Dan creates real and Demo records through the UI; this design work must not populate, remove or silently convert existing records.

## Implemented workflow

1. No saved budgets: show the empty collection with Create budget. Creating opens a manual editor with Name, Type (Income/Expense/Savings), Amount and Frequency. Budget name and currency are in the top plan bar. Add entry is the primary editor action; From transactions is an alternative. No seed entries are persisted.
2. Saved budget: a searchable budget dropdown supports any number of plans; New budget is separate. Rename edits the name in the same top bar, with explicit Save/Discard; there is no duplicate name row. A visible Active badge identifies the plan used by other screens. Browsing an inactive plan never activates it.
3. Main surface: compact editable entry table, four prominent monthly summary figures (income, expenses excluding savings, planned savings, available to spend), and a visual breakdown by entry. Annual equivalents remain secondary. Keep income, ordinary expenses and savings distinguishable with text as well as colour. Show a negative available-to-spend amount as a shortfall, never clamp it to zero. Group actions beside the table; use a row menu for deletion rather than a prominent Delete on every card. On mobile entries become labelled stacked rows.
4. New plans remain inactive until the user explicitly chooses Make active. Allow no active plan before that choice; otherwise at most one per workspace. Activating a plan atomically replaces the previous selection. Dashboard bank income/spending remains actual bank data; only planned amounts, budget comparisons and later projections consult the active plan.
5. From transactions: if budgets exist, offer Merge into a budget (select target) or Create new budget (name). Show a review table with suggested entries, source window/coverage and proposed matches. Each suggestion can add a new entry, update a chosen existing entry, or be skipped. Default to preserving existing values; require an explicit choice for updates. A matching name alone cannot authorize merging. Nothing saves until the user commits the reviewed changes.
6. Annual and monthly equivalents are planning averages, not bill due dates. Store the entered amount and interval exactly; divide by 1/3/6/12 for monthly equivalents, and multiply by 12/interval for annual totals. Aggregate unrounded decimal values, then format currency. Do not sum currencies or round each monthly average before aggregating.

Illustrative design-only expenses: Housing 7,800/month, Groceries 3,000/month, Internet 1,000/3 months, Insurance 4,200/6 months, Subscriptions 1,200/year, Transport 800/month. Monthly equivalent DKK 12,733.33; annual total DKK 152,800.00. These are fictional visual examples, not new product records.

Calculation contract: normalize each entry to an unrounded monthly equivalent. I is the sum of Income entries; E is the sum of Expense entries without the Savings marker; S is the sum of Expense entries with the Savings marker. Available to spend = I − E − S. Savings is counted exactly once. If a separate total of all Expense-type entries is ever shown, it is E + S, and available to spend is I minus that combined total. Amounts are nonnegative magnitudes; Type determines their role. Savings cannot be marked on Income entries. Empty/incomplete drafts must not imply a complete financial picture.

Illustrative arithmetic check only: DKK 30,000 monthly income, DKK 12,733.33 monthly-equivalent ordinary expenses and DKK 4,000 planned savings leave DKK 13,266.67 available to spend. Annual values are 360,000 − 152,800 − 48,000 = 159,200. No example records are to be created. Saving toward another owned account remains a planned allocation; it must not reclassify an actual internal transfer as bank spending or count the receiving leg as bank income.

## Implemented model and remaining scope

- BudgetPlan: stable ID, name, currency, timestamps and rowversion, scoped to the selected workspace database.
- BudgetEntry: plan ID, name, type (Income/Expense), isSavings (valid only for Expense), entered amount, intervalMonths (1/3/6/12), order, source/history-window provenance and rowversion. Transaction/category mapping is deferred; the current editor requires no category.
- Active selection is implemented as BudgetPlan.IsActive with a unique filtered SQL index, rather than a separate settings row. Serializable activation checks the expected current active ID and target rowversion, then atomically changes the selection. Zero or one active budget per workspace; no global selection across Demo and Dan.
- Suggestion preview: target/new-plan intent, candidate entries, source coverage and explicit add/update/skip decisions. Validate target versions again on save; retries must not duplicate entries. No actual AI is required.
- Local migration 20260907200740_NamedBudgetPlans adds BudgetPlans and BudgetEntries only. Full-plan saves validate entry ownership and parent rowversion, persist last request ID/hash for safe immediate retries, and apply entry additions/updates/removals atomically. Encrypted backup/restore includes both new tables and supports older archives with neither table.
- Transaction suggestions average the absolute booked amounts by exact description and sign over 1–12 completed months, including zero-activity months. Confirmed internal transfers and reservations are excluded. Credits are suggested separately and explicitly require review for refunds/unmatched transfers. Insufficient history suppresses proposed amounts. Frequency defaults to a monthly average, not an inferred billing interval. The read is bounded to 50,000 transactions, 100 accounts and 200 suggestion groups; excess produces an explicit limit error.
- Merge defaults to Skip for a matching name/type and Add for unmatched suggestions. Update requires an explicit selected same-type entry, preserves its name/frequency/Savings marker, and converts the suggested monthly amount to that billing interval. Continue to editor creates only an in-memory draft. Final Save is required; a stale target version rejects the entire save without overwriting newer data. No separate persisted preview entity is needed for this local workflow.
- The Overview reads the active plan and displays a separate planned-monthly section using the plan currency. It does not replace bank actuals or claim per-entry actual-spending mapping. Browsing a plan never activates it; deleting an active plan requires explicit deactivation first.
- Legacy category-period limits are preserved unchanged and accessible through a read-only Previous category limits page. No automatic conversion or active selection; the eight historical Demo limits are not eight named plans.
- Compare/projections remain later scope; no fake charts or inactive controls suggesting those features already work. Azure/deployment still requires separate approval after local acceptance.

## Open details before dependent implementation

- Bill timing: a frequency alone does not specify the next due month. Add a start/due-month anchor when actual cash-flow projections are built; do not invent bill schedules now.
- Actual spending per named entry needs an explicit, non-overlapping transaction mapping. Multiple entries in one category cannot each receive all of that category's spending. Until mapped, show planned values and honest unmatched coverage.
- Existing-record conversion and active-plan change history/effective dates need a deliberate migration design. Historical actual transactions must never change when a different plan becomes active.
