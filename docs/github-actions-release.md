# GitHub Actions release route

The `publish-banking.yml` workflow builds and validates an immutable package from the current `main` commit. Main pushes always run the build and tests. Publishing runs only when the repository variable `BANKING_AZURE_DEPLOY_ENABLED` is exactly `true`; a manual dispatch also requires the operator to enter `DEPLOY`. Dispatch accepts a full source SHA, and both paths fail unless it is the exact current `main` SHA. Production runs are serialized and cannot be canceled by a newer run.

The deploy job uses GitHub OIDC and Entra ID. It requests an ARM token from Azure CLI and uses it as a bearer token only for the fixed SCM host. Basic publishing credentials, client secrets, GitHub environments, and arbitrary target inputs are not used. The artifact is downloaded by immutable artifact ID using the job's read-only GitHub token; the complete outer ZIP SHA-256 must equal the upload action's digest before its three allowed files are extracted. The package manifest and archive checksums, file inventory, source SHA, build stamp, artifact digest, terminal deployment record, health/runtime response, unauthenticated account denial, API/advisor/Node file hashes and Node version, public asset hashes, and the complete CSP are checked before success.

The Azure principal is dedicated to this workflow. Its federated credential must use issuer `https://token.actions.githubusercontent.com`, audience `api://AzureADTokenExchange`, and subject `repo:DanAakesen/Banking:ref:refs/heads/main`. Before each upload, the workflow stores a snapshot of the current `/home/site/wwwroot` inside the App Service at `/home/Banking/releases/before-<source-sha>.zip`. The snapshot never leaves Azure. It records only the remote path, hash, size, prior build, deployment ID, and public asset hashes in the GitHub evidence artifact. If the new deployment reaches a terminal state but deployment or post-deployment gates fail, the helper verifies the backup hash, restores the prior files in place, restarts the app, and checks the prior build and public assets. This file restore does not create a new Kudu deployment record. If deployment status is unknown or still running, it does not start a concurrent rollback; inspect the App Service deployment state before retrying. Evidence artifacts contain JSON metadata only.

The workflow does not alter App Service settings, secrets, database schema, customer records, or financial data. Before live ZIP deployment, it copies the checksum-verified package to `/home/Banking/releases/<source-sha>.zip`, unpacks it to the sibling staging directory, verifies the remote archive checksum, and runs `dotnet Banking.Api.dll --verify-pension-schema` from that staged directory. This read-only gate checks that the required pension migration, tables and wealth-record column already exist in both Demo and Live databases; it must not read financial rows or perform DDL. A missing schema or verification error stops before the live upload. Schema creation remains a separate Main-coordinated `CloudImport.Schema` operator action; the deployment workflow never applies migrations or grants database permissions. A prior deployment showed Kudu reporting ZIP deployment status `4` while the App Service continued serving its previous runtime until restarted. After terminal ZIP deployment and deployed-file hash verification, the helper therefore issues one explicit restart of the fixed App Service, records `controlledRestartIssued: true` only after Azure CLI returns success, then allows up to 180 seconds for the expected build and health response. Restart failure enters the same terminal-state rollback path. The read-only post-deployment smoke creates a fresh in-memory public Demo session, verifies the product-demo connection, synthetic accounts and monthly aggregate/category parity, and requires anonymous Live `401` plus Demo-to-Live `403`. Unexpectedly successful private reads are closed without consuming their payload. The sole POST creates the Demo session; no financial repair is rerun. Embedded Codex annotation acceptance remains a separate browser review after publication.
